源码解析

带 type 的字典被视为 EngineInput，直接保留；普通原始 prompt 则走兼容预处理分支。本版本明确提示：更推荐由 Renderer.render_cmpl / render_chat 先产生标准输入，不能把所有模板渲染和 tokenization 都归到 InputProcessor 内部。

逐步拆解

  1. arrival_time 未传入时，从标准输入读取，或在后续兼容分支使用当前时间。它是请求元数据，不是模型的 token 位置。
  2. 赋值 engine_input=prompt 不执行模型，也不意味着略过校验；后面仍调用平台和模型输入校验。类型标签解决“输入是什么形态”，不是对内容合法性的保证。
通俗理解

接待员先看你拿来的是填好的标准表，还是一段口述材料。标准表可以继续办理，口述材料还要先整理；拿到标准表也不代表可以跳过审核。

源码解析

decoder_input 的类型决定从哪里取模型输入。embeds 分支保留 prompt_embeds 及可选 token IDs；普通 token 分支直接取 token IDs，并清空 embedding 相关项。随后为生成任务复制 SamplingParams。

逐步拆解

  1. 不能假设每个请求都有完整 prompt_token_ids：输入 embedding 是另一路合法形态，相关长度、哈希与校验要按对应逻辑处理。
  2. params.clone() 产生请求自己的参数副本。调用方可能复用同一个参数对象，后续补默认值或调整停止参数时不应改变其他请求的配置。
通俗理解

有人交的是文字编号，有人交的是已经转换好的向量材料；内部表单要记录正确的一种。每份工单再复印一份自己的操作要求，避免改一份就连带改了其他人的要求。

源码解析

仅在 max_tokens 未指定时，用 max_model_len−prompt_len 得到默认可生成长度。补齐后检查 min_tokens 是否超过 max_tokens，矛盾的请求直接报错。

逐步拆解

  1. 例如模型上下文上限 100、prompt 长 80，未指定 max_tokens 时默认上限为 20；这不是本轮 Scheduler 的 token_budget，而是该请求允许产生的输出数量。
  2. 显式传入 max_tokens 的其他校验不在此片段。阅读 if 的条件很重要：不能由这个默认值分支推断所有请求都在这里被强制改写。
通俗理解

一本册子能写 100 页，输入已经用了 80 页，用户又没说最多续写多少，就按剩余 20 页设置上限。如果同时要求至少写 30 页，这个要求本身就无法满足。

通俗理解

源码解析

EngineCoreRequest 把请求 ID、token/embedding 输入、多模态特征、生成或 pooling 参数、到达时间与优先级等集中起来。它是跨越前端到核心的标准载体。

逐步拆解

  1. prompt_token_ids 与 prompt_embeds 的具体有效组合由前面的分支决定；这里打包不是重新做 tokenization。
  2. cache_salt 来自 decoder_input，供后续缓存隔离相关逻辑使用；priority 交给调度策略解释。它们都不是模型前向的词表输入。
通俗理解

把原料、加工要求、订单编号和优先级装进同一份工单。接单部门不用再重新理解顾客的原话，而是依据结构化字段继续处理。

源码解析

构造器尾部附上 data_parallel_rank、trace_headers、resumable、session_id 与 kv_hints。这些字段服务路由、观测、输入续接和缓存提示等控制需求。

  1. data_parallel_rank 是输入到核心体系的路由信息，最终怎样选择目标 engine 由相应客户端路径决定，不是让一个 token 自动分配到某张 GPU。

通俗理解

工单上的收件部门、追踪编号和“后面还会补材料”标记，帮助系统把单送对并持续跟进。填完这些只是准备发送，并不是菜已经做好了。
