源码解析

没有启用该请求的前缀查询时直接返回空块及零命中。否则取得请求允许的最大命中长度，再按 block_hashes 向 coordinator 查询最长可复用前缀。

逐步拆解

  1. 这里命中的是已有 KV 对应的输入计算，不是用户问题与答案的文本缓存。相同字符也不直接等价于相同 block hash，缓存资格由完整上下文相关逻辑决定。

通俗理解

02 · 算出需要覆盖的位置，再检查空间

源码解析

num_local_computed_tokens 把请求原有进度与新采用的本地前缀命中相加；total_computed_tokens 再加外部命中并受 max_model_len 限制。变量名相似，但包含的来源不同。

逐步拆解

  1. 已有请求进度、新发现的本地命中、远端 connector 提供的计算量分别传递。把某段命中同时算到多个来源，会把位置起点推得过远。
  2. 例如原有进度 4，新本地命中 4，外部命中 0，则本地与总计算量都是 8。这个教学数字只解释相加关系；哪些组合可出现仍由接纳与 connector 流程约束。
通俗理解

先盘点自己已做的部分，再登记刚借到的本地资料，最后加上其他部门送来的成果。每份成果只能记一次，否则账上会显示任务已经完成，实际却缺了内容。

  2. lookahead 只是空间需求，不能当作已确认生成结果。滑窗等模型可以不再需要一部分旧块，普通 full attention 则有不同的保留需求。
通俗理解

源码解析

  2. 此处展示前缀关联，接下来的 allocate_new_blocks 再扩展新空间。执行侧要到真正前向或远端加载完成时，才具备相应的实际 KV 内容。
通俗理解

先确认整项任务能安排得下，再把借来的资料登记到这个订单，随后给接下来的工作分配空桌面。借资料和准备空桌面是两件不同的事。

04 · 请求结束后，块是否真的消失？

KVCacheManager.free：把释放交给 coordinatorcore/kv_cache_manager.py · L628–637 ↗
628    def free(self, request: Request) -> None:629        """Free the blocks allocated for the request.630        We free the blocks in reverse order so that the tail blocks are evicted631        first when caching is enabled.632633        Args:634            request: The request to free the blocks.635636        """637        self.coordinator.free(request.request_id)
源码解析

请求释放入口按 request_id 委托 coordinator。注释说明调用侧的释放顺序意图让尾部块更早具备淘汰机会，具体空闲队列策略还要继续看 BlockPool。

逐步拆解

  1. 这段没有对 GPU tensor 执行清零，也没有逐元素删除 KV。请求结束首先是解除资源持有关系，而不是擦除所有物理内容。
  2. 共享前缀可能仍有其他请求持有；即使引用降为零，保留着哈希的缓存块也可继续留待复用或被淘汰。
通俗理解

归还柜子首先是注销你对柜子的占用。里面的资料是否保留供下次借用，要看资料室规则，而不是每次还柜子就把整座仓库里的东西都销毁。

  2. 没有哈希或未启用缓存的块优先复用；有缓存价值的块后置，保留被再次命中的机会。这里前置与后置的是空闲队列顺序，不是直接修改 token 的逻辑顺序。
通俗理解
