EngineCore · 核心主循环

把配置、缓存、请求、调度与执行串成一个持续运转的核心。

输入 → 处理 → 输出

输入消息 → Request → Scheduler → Executor → Scheduler 回写 → 按客户端输出；启动阶段先确定 KV 配置

源码解析

前面已收集各 Worker 的 KV 规格和可用内存，这里据此生成缓存配置。如果自动适配改变 max_model_len，要同步给已启动的 Worker，随后生成 Scheduler 使用的缓存视图。

逐步拆解

  1. Worker 的 KV 配置描述设备侧布局需求，scheduler_kv_cache_config 面向核心分配管理。二者来自同一初始化过程，避免 CPU 认为可分配的块数与设备实际能力不一致。

通俗理解

先测量各车间有多少工作台，再给总调度室一张一致的资源表。如果实际空间迫使产品尺寸变小，也要通知已经开工准备的车间，不能两边各记一套尺寸。

源码解析

核心进程在关闭状态允许时循环：处理输入队列，更新负载统计，执行一步，再更新统计。输入队列函数负责决定什么时候可以进入下一步，并不表示这里无条件空转。

逐步拆解

  1. 执行前后都发布请求计数是为了提高负载状态的新鲜度；DP 路由需要的是当前排队与执行情况，而非只在启动时采样一次。
  2. 普通 EngineCoreProc 的循环是这里的主线，DP 子类另有专用行为。进程内客户端也不靠这一独立进程循环，而是在 get_output 中推进 step_fn。
通俗理解

值班经理不断重复“收新单、看负载、推动一轮制作、再看负载”。如果改成现场窗口办理，推动方式会不同，但核心处理职责仍然在。

04 · 输出投递与没有前向时的工作

源码解析

通过 step_fn 执行本轮，将输出字典中的项目放入 output_queue，然后调用 post_step。这个队列是核心到输出传输链路的衔接点。

逐步拆解

  1. outputs.items() 保存客户端标识与对应结果的组合；多个客户端共享核心时，不能把所有结果随意合并成无归属的 token 列表。
  2. model_executed 作为独立返回状态交给 post_step，说明“这轮是否执行模型”与“这轮有没有输出对象”是两个不同问题。
通俗理解

结果装好后按分店分堆，再送到发件区。经理还会记下这一轮机器有没有实际开动；有通知要发和机器正在加工，并不是同一件事。

源码解析

如果没有模型执行，但 Scheduler 仍有工作，例如等待远端 KV 或延迟释放，核心短暂 sleep。其目的不是模拟 GPU 计算，而是让后台线程能够推进。

通俗理解
