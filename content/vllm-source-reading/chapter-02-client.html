EngineCoreClient · 核心通信

用统一接口隐藏进程内调用与多进程消息传递。

输入 → 处理 → 输出

EngineCoreRequest → ADD / ABORT / UTILITY 消息 → EngineCore；EngineCoreOutputs → 异步输出队列 → 前端

源码解析

asyncio 模式与非多进程组合在这里明确不支持；多进程加 asyncio 则选择异步多进程客户端工厂。接口名字相似，不代表四种组合都可随意使用。

逐步拆解

  1. 第一个分支直接抛 NotImplementedError，因此不能把 asyncio=True 理解为对所有后端自动加一层协程包装。
  2. make_async_mp_client 还可以按配置选择进一步的实现，本节后续展示 AsyncMPClient 的基础收发路径，不覆盖全部 DP 负载均衡分支。
通俗理解

同一个客服窗口背后可能是现场办理，也可能转给远处的办事中心。系统先选择可用的办理方式，不能随意拼接一个当前不支持的组合。

  1. 区别主要是调用与通信组织方式，不代表使用 InprocClient 就跳过 Scheduler 或不需要 Worker 执行抽象。
  2. 这一返回值让上游围绕统一客户端接口编程。切换部署方式时，请求语义保持一致，具体传递路径由实现承担。
通俗理解

上层只说“提交订单、取结果”，不用每次重新决定是隔着柜台递纸，还是通过内部邮路送到另一个部门。

02 · 进程内路径的真实调用

InprocClient：直接接纳、取消与关闭engine/core_client.py · L416–426 ↗
416    def add_request(self, request: EngineCoreRequest) -> None:417        req, request_wave = self.engine_core.preprocess_add_request(request)418        self.engine_core.add_request(req, request_wave)419420    def abort_requests(self, request_ids: list[str]) -> None:421        if len(request_ids) > 0:422            self.engine_core.abort_requests(request_ids)423424    def shutdown(self, timeout: float | None = None) -> None:425        if self._finalizer.detach() is not None:426            self.engine_core.shutdown()
源码解析

进程内提交先调用 preprocess_add_request 把传输对象转成调度侧对象，再交给 EngineCore.add_request。取消请求则直接委托核心；shutdown 通过 finalizer 状态避免重复触发同一路清理。

逐步拆解

  1. 提交完成并不等于生成完成：add_request 只把任务送进核心生命周期，之后还需要 step_fn 推动调度与执行。
  2. abort_requests 对空列表不执行额外操作。此处没有通过 socket 序列化，不应把进程内调用画成必经 IPC。
通俗理解

同在一个办公室时可以直接把单交给同事，无需装信封寄送。但同事收到了单，仍要排期干活，不会在接单瞬间就得到结果。

InprocClient：取输出同时推进核心一步engine/core_client.py · L408–411 ↗
408    def get_output(self) -> EngineCoreOutputs:409        outputs, model_executed = self.engine_core.step_fn()410        self.engine_core.post_step(model_executed=model_executed)411        return outputs and outputs.get(0) or EngineCoreOutputs()
源码解析

get_output 调用 step_fn，再运行 post_step，最后取 client 0 的输出或返回空 EngineCoreOutputs。这条路径里，“取输出”本身就参与驱动引擎。

逐步拆解

  1. step_fn 可以由配置选择不同 step 实现；不要把这里的函数指针硬解释为永远只调用普通 step。
  2. 没有本轮客户端结果不等于一定没有任何计算。分块 prefill、维护工作等可能推动内部状态但暂时无可见输出。
通俗理解

现场办理时，你问一次进度，窗口就按当前工作流程推进一轮，再给你这一轮能拿到的材料。有时后台做了准备工作，却还没有可交付的答案。

03 · 把请求变成消息并发送

AsyncMPClient：ADD 与 ABORTengine/core_client.py · L1349–1356 ↗

源码解析

提交时把 client_index 写入请求，发送 ADD 消息，并确保输出接收任务已启动。取消则发送 ABORT，且只在 ID 非空、engine 未标记死亡时执行。

逐步拆解

  1. client_index 供核心把输出路由回正确的客户端；request_id 则区分具体请求，二者不是同一层级的标识。
  2. await 等待的是这个发送调用的完成，不是完整生成结束。返回结果由另一条接收链路交付，所以提交和消费输出可以解耦。
通俗理解

订单写上分店编号和订单号后发出去，客服就可以继续接别的单。等待邮寄成功，不等于等待厨房把整道菜做完。

未显式指定 engine 时使用 core_engine；消息由请求类型标记和编码后的内容组成，再前置 engine 身份发送。ensure_alive 在真正发出前检查核心可用性。

逐步拆解

  1. copy=False 是这条 ZMQ 发送路径的拷贝策略。注释说明张量/数组帧的生命周期由底层引用链维持，但不意味着从 Python 对象到 GPU 全链路都没有拷贝。
  2. ADD 与 ABORT 使用同一消息框架，通过类型值区分。它们携带控制信息或请求数据，不应与模型并行中的 tensor 通信混为一谈。
通俗理解

先写收件地址，再标明这是新订单还是取消单，然后把内容装成可以传递的格式。多帧像一份信附了几张附件；少复制附件，并不表示附件已经自动进了厨房的机器。

04 · 接收结果与管理调用的返回

源码解析

前端消费者从 outputs_queue 异步等待。后台输出接收任务如果失败，可以把异常投递到同一队列；这里识别后格式化并抛出。

逐步拆解

  1. await queue.get() 在无输出时挂起当前协程，不需要前端反复忙轮询；接收任务与调用者通过队列衔接。
  2. 返回的是 EngineCoreOutputs，仍然是核心结果形态。把 token 变成文本和用户侧 RequestOutput，属于后续 OutputProcessor。
通俗理解

前台坐在收件箱旁等通知，有信就处理；如果运输故障，箱子里也会收到错误通知。它不会把“没有成功送达”当成正常的空答案悄悄吞掉。
